# n8n 内网 Human-in-the-Loop 场景评估

## 一、我的使用场景

- 在内网环境下使用。
- 使用的 Agent CLI 是内部工具。
- Agent CLI 使用时，有数据和权限校验要求。
- 如果在容器中或挂载到容器中使用 Agent CLI，会有权限校验不过的问题。
- 需求：在办公电脑上直接运行，从而直接调用本地的工具。

## 二、n8n 介绍

### 2.1 n8n 是什么？

n8n 是一个成熟的通用工作流自动化平台，但它与 LangGraph 和 Langflow 在定位上有本质区别：**n8n 并非专为 AI Agent 设计，而是一个通用的低代码自动化工具，AI 能力是其近年新增的扩展功能**。这意味着它在 HITL 和本地集成方面有独特优势，但在纯 AI 工作流编排的深度上可能不如前两者。

n8n 是一个开源的工作流自动化平台，通过可视化拖拽界面连接应用、服务和 API，支持用 JavaScript 扩展自定义逻辑。其核心定位如下：

| 维度 | 说明 |
|-|-|
| 本质 | 通用工作流自动化平台（低代码），AI 能力为扩展功能 |
| 核心优势 | 400+ 集成节点、可视化拖拽、高度可自托管 |
| AI 能力 | 通过 AI Agent 节点、LangChain 集成支持 LLM 工作流 |
| 本地运行 | 支持 npm 直接安装（无需 Docker）或 Docker 部署 |
| HITL 支持 | 通过 **Human Review** 工具审批 + **Wait 节点**实现 |
| 开源协议 | Sustainable Use License（源码可见，非严格开源） |

n8n 与 LangGraph/Langflow 的关键差异在于：LangGraph 是**代码优先的编排框架**，Langflow 是**AI 工作流可视化平台**，而 n8n 是**通用自动化平台**，AI 只是它可以编排的众多节点类型之一。

### 2.2 Human-in-the-Loop (HITL) 的工作机制

n8n 的 HITL 实现**不依赖单一机制，而是通过组合不同节点来实现灵活的人工介入**。主要有两种模式：

#### 模式一：AI Agent 的 Human Review（工具审批）

这是 n8n 原生支持 AI 场景的 HITL 方式。当 AI Agent 尝试调用某个标记为需要人工审核的工具时，工作流暂停，并通过配置的渠道（Slack、Telegram、n8n Chat、Email 等）发送审批请求。

工作流程：

1. **AI Agent 决定调用工具** → 该工具已启用 Human Review
2. **工作流暂停**，发送审批请求，包含工具名称和 AI 准备使用的参数
3. **审核人批准或拒绝**：批准则工具按 AI 指定参数执行；拒绝则取消操作并通知 AI
4. **可选渠道分离**：用户可在 n8n Chat 中与 AI 交互，但审批请求路由到特定人员的 Slack

配置方式：在 AI Agent 节点的 Tools Panel 中找到 Human review 区域，选择审批渠道并连接需要审核的工具。可使用 `$tool.name` 和 `$tool.parameters` 变量构建包含上下文的审批消息。

#### 模式二：Wait 节点的通用人工介入

对于非 AI 场景或需要更灵活控制的情况，n8n 提供 **Wait 节点**作为通用的人工暂停机制。典型模式为：

1. **Webhook 触发** → **HTTP Request**（发送审批请求）→ **Wait 节点**（暂停，等待 Webhook 回调）→ **IF 节点**（根据审批结果分支）
2. Wait 节点支持 `Resume: On Webhook Call`，n8n 自动提供 `$execution.resumeUrl` 用于恢复
3. 可结合超时设置，避免工作流无限期挂起

社区节点如 `n8n-nodes-velatir` 和 `n8n-nodes-approve` 提供了额外的审批门控选项，支持轮询和决策路由。

## 三、是否适合我的场景？（匹配度分析）

| 我的需求 | n8n 的支持情况 | 关键细节 |
|-|-|-|
| 内网环境使用 | ✅ 支持 | n8n 可完全离线运行，通过设置环境变量禁用遥测、版本检查和服务调用。官方明确支持 **air-gapped（气隙隔离）私有网络部署**。 |
| 内部 Agent CLI 对接 | ⚠️ 部分支持 | n8n 有 REST API 和 MCP 服务器，CLI 可作为 MCP 客户端连接并调用工作流。也有社区 CLI 工具（如 `n8n-cli`）支持 AI Agent 程序化创建和验证工作流。但 **n8n 不是为 CLI 触发而设计的**，其核心触发方式是 Webhook、Schedule 和 App 事件。CLI 触发需要通过 API 间接实现。 |
| 数据和权限校验 | ✅ 支持 | 自托管 n8n 支持 **SSO、SAML、LDAP** 对接现有认证服务。可配置**细粒度的项目级访问规则**，精确控制每个用户/团队/API 的查看、编辑、发布权限。支持**第三方密钥管理**（1Password、HashiCorp Vault 等）。Webhook 入口支持 Basic、Header 或 JWT 认证。 |
| 办公电脑直接运行，调用本地工具 | ✅ 完全支持 | **Execute Command 节点**可直接运行 Shell 脚本（`bash /path/to/script.sh`）或 Python 脚本（`python /path/to/script.py`），脚本输出捕获到 `$json.stdout`。可通过 npm 直接安装，**无需 Docker**。也有社区封装的“绿色版”解压即用。 |
| 不依赖容器 | ✅ 支持 | npm 安装将 n8n 直接安装在操作系统上，无容器开销。但需注意：npm 安装**默认不保留工作流和数据**，需要额外配置持久化。 |

## 四、需要留意的关键点

1. **离线环境下集成节点的局限性**：n8n 的 400+ 集成节点中，**绝大多数是云 API 的封装**（Google、Slack、Notion 等）。在完全离线的内网中，这些节点**无法使用**。你真正能用的是：Execute Command 节点、Code 节点、HTTP Request 节点（指向内网服务）、本地文件读写节点，以及本地 LLM（Ollama）集成。

2. **CLI 触发的非原生性**：n8n 的核心交互方式是 Web UI 和 Webhook。如果你的内部 Agent CLI 需要作为主要触发入口，需要通过 n8n 的 REST API 或 MCP 服务器间接实现，**不如 LangGraph 那样将 CLI 作为一等公民**。

3. **安全漏洞历史**：n8n 曾披露多个高危漏洞，包括授权绕过（CVE-2026-54307/54308）和 Execute Sub-workflow 节点中的凭据验证缺失（JVNDB-2026-031451）。在内网使用前，**务必升级到最新安全版本**。

4. **许可限制**：n8n 使用 Sustainable Use License，**源码可见但非严格开源**。企业级功能（SSO、细粒度 RBAC 等）需要企业版许可，在气隙环境中联系 n8n 获取许可可能受限。

5. **Execute Command 的安全风险**：赋予 n8n 执行系统命令的能力时，**必须防止命令注入**。不要直接拼接外部输入到命令字符串，建议使用参数化或严格校验，并限制 Execute Command 节点的使用权限。

## 五、综合结论

**n8n 部分适合你的场景，但需要清醒认识其定位差异。**

| 维度 | 评估 |
|-|-|
| 内网离线运行 | ✅ 完全可行，官方支持气隙部署 |
| 本地工具调用 | ✅ Execute Command 节点直接调用本地脚本和命令 |
| 权限校验 | ✅ 企业版提供 SSO/LDAP/细粒度 RBAC，但需许可 |
| CLI 作为主要触发入口 | ⚠️ 非原生，需通过 API/MCP 间接实现 |
| HITL 机制 | ✅ 灵活（Human Review + Wait 节点），但偏通用自动化而非 Agent 编排 |

**推荐组合方案**：如果你坚持 CLI 触发 + 本地工具调用的核心需求，可以考虑 **LangGraph 作为 Agent 编排引擎（CLI 原生集成、HITL 深度支持）+ n8n 作为执行层**（通过 HTTP Request 节点调用 n8n Webhook，由 n8n 负责调用本地工具和集成内网服务）。这样兼顾了 LangGraph 在 Agent 编排和 CLI 集成上的优势，以及 n8n 在通用自动化和本地工具调用上的成熟度。
