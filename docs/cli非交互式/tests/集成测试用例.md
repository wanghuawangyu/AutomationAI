## 测试通用规则

- 导出按钮：未选目录时必须置灰不可点击
- 导出写入：选完目录后直接写入该目录，不触发浏览器下载
- 分页：默认每页 10 条，可选 10/50/100/1000 条，右下角对齐
- 展开/折叠：点击展开后行内展示详情；再次点击折叠；展开另一行时自动折叠上一行

### 往返保真校验（基准快照 B）

所有「生命周期（新建→…→导出→删除→导入）」类用例，均采用统一的**往返保真**校验口径（模板见 TC-C1a）：

- **基准快照 B**：第 1 步填写完成后，逐字记录所有可编辑字段值（含界面标签），作为后续全部比对的唯一基准。
- **校验点**：①保存后列表行展示；②再次进入**编辑界面回显**；③**复制**副本的编辑界面回显；④**导出 YAML** 内容；⑤**导入后**查看界面（列表行内展开详情）+ 再次进入编辑界面回显。
- **比对口径**：
  - 界面 ↔ B：逐字段一致（类型/名称/描述/专有字段）。
  - 导出的 YAML ↔ B：字段名以 API/导出口径为准（如 `argsTemplate`/`exitCodeSuccess` 以 JSON 字符串/数组表示），按**等价内容**判断，不因引号或格式差异判为不一致；**不应出现该类型无有的字段**（prompt 无 `binaryPath`；脚本类无 `command`/`argsTemplate`/`inputMode`/`outputMode`/`outputJsonPath`）。
  - 名称冲突：导入到已存在同名的环境时，按「导入冲突」处理（提示冲突），不视为一致性失败。
- **修改分支**：若用例在某步选择「修改并保存」，则 B 的对应字段**同步更新为修改后值**，后续按更新后的 B 比对；默认（不修改）路径下 B 始终等于第 1 步填写值。

## 优先级定义

| 级别 | 含义             | 说明                                               |
| ---- | ---------------- | -------------------------------------------------- |
| P0   | 依赖静态数据测试 | 用**预置静态数据**即可验证（前端 mock 数据，或一次性导入 fixtures / DB 注入 seed.sql）——不依赖定时、重启等**时序条件**；个别子项需一次性预置（如 TC-J2「最近执行失败」的 seed.sql 注入）已在用例前置标注。**时间筛选类数据集因期望相对当前时刻，归 P1**             |
| P1   | 依赖后端测试     | 需要真实后端 API 返回数据才能验证（CRUD / 导入导出 / 真实数据渲染）                  |
| P2   | 依赖后端执行/定时 | 需要真实后端**执行器或调度器**产生结果才能验证（单次执行 / Job 运行 / 到点自动触发——后者需等待定时触发）             |
| P3   | 异常场景测试     | 需要构造失败/长耗时/版本变更等特殊场景验证异常流程 |

#### TC-C1a Client 生命周期（prompt 类型）

- **优先级**：P1
- **用例目标**：验证 prompt 类型 Client 从创建到删除导入的完整生命周期，并以「第 1 步填写的信息」为**基准快照 B**，逐一校验后续各阶段（保存后列表、编辑界面回显、复制副本、导出 YAML、导入后列表与编辑界面）展示的信息与 B 一致（往返保真）。
- **前置条件**：进入 Client 管理页。

**基准快照 B（第 1 步填写完成后立即逐字记录，后续所有比对以 B 为准）**

| 字段 | 界面标签 | 填写值（示例，可由测试环境自定） |
|-|-|-|
| `name` | 名称 | `tc_c1a_prompt` |
| `description` | 描述 | `TC-C1a prompt 生命周期` |
| `type` | 类型 | prompt |
| `command` | 命令 | `claude` |
| `argsTemplate` | 参数模板 | `--print --output-format json --model sonnet` |
| `inputMode` | 输入方式 | `stdin` |
| `outputMode` | 输出解析 mode | `json` |
| `outputJsonPath` | jsonPath | `$.result` |
| `exitCodeSuccess` | 退出码语义（成功） | `0` |

> 比对口径：
> - 「参数模板」「退出码语义」在导出的 YAML 中分别以 **JSON 字符串 / 数组**表示（如 `"--print ..."` / `[0]`），按**等价内容**判断，不因引号或格式差异判为不一致。
> - prompt 类型**不含** `binaryPath`；只有脚本类（bash / python / powershell）才显示二进制路径。
> - 第 4 步若选择「修改并保存」，则 B 中对应字段**同步更新为修改后值**，后续步骤按更新后的 B 比对；默认（不修改）路径下 B 始终等于第 1 步填写值。

- **执行步骤与预期结果**：
  1. 点击 [＋ 新建]，类型选 prompt，填写名称、描述、命令、参数模板、输入方式、输出解析 mode、jsonPath、退出码语义
     → 预期：编辑表单显示 prompt 专用字段（名称 / 描述 / 命令 / 参数模板 / 输入方式 / 输出解析 mode / jsonPath / 退出码语义）；**填写完成后立即记录基准快照 B（上表）**。
  2. 点击 [测试命令]
     → 预期：弹出测试对话框，显示类型、命令、参数与运行结果，验证命令可执行。
  3. 点击 [保存]
     → 预期：列表新增一行，类型=prompt；列表行展示与 B 一致（名称 = B.name；输入方式列显示「参数模板: B.argsTemplate」；输出解析列显示 `json`）。
  4. 点击该行 [编辑]
     → 预期（**回显一致性**）：编辑界面各字段与基准快照 B **完全一致**——名称 = B.name、描述 = B.description、类型 = prompt、命令 = B.command、参数模板 = B.argsTemplate、输入方式 = B.inputMode、输出解析 mode = B.outputMode、jsonPath = B.outputJsonPath、退出码语义 = B.exitCodeSuccess。

       - 4.2（默认）仅回显校验后免改返回，B 保持不变。
  5. 点击该行 [复制]
     → 预期：基于该 Client 新增一条副本并**自动进入编辑界面**；**编辑界面各字段与基准快照 B 一致**，仅 `name` 为副本名（`B.name + '_copy'` 或带「副本」后缀）。
       - 5.1 返回列表，副本行（类型、输入方式、输出解析）同样与 B 一致（名称除外）。
  6. 点击第 3 步创建的那一行 [导出]，**不选目录**
     → 预期：[导出] 按钮置灰不可点击（未选目录时不可导出）。
  7. 选目录后点击 [导出]

       | YAML 字段 | 应等于 | 校验点 |
       |-|-|-|
       | `name` | B.name | 一致 |
       | `type` | prompt | 一致 |
       | `description` | B.description | 一致 |
       | `command` | B.command | 一致 |
       | `inputMode` | B.inputMode | 一致 |
       | `argsTemplate` | B.argsTemplate | 内容等价（JSON 字符串形式） |
       | `outputMode` | B.outputMode | 一致 |
       | `outputJsonPath` | B.outputJsonPath | 一致 |
       | `exitCodeSuccess` | B.exitCodeSuccess | 等价（如 `[0]`） |
       | `binaryPath` | — | **不应出现**（prompt 类型无此字段） |

       - 7.1 记录该 YAML 的完整路径，供第 9 步导入使用。
  8. 删除该 Client
     → 预期：确认后列表中该行消失；（如有副本）副本行不受影响。
  9. 点击 [导入]，选择第 7 步导出的 YAML
     → 预期（**导入保真**）：列表刷新，新增对应 Client。
       - 9.1 **查看界面（列表行内展开详情）**与基准快照 B **一致**：类型=prompt、`command`、`inputMode`、`outputMode`/`outputJsonPath`、`argsTemplate`、`description` 均可回显，名称与 B 一致（若环境已存在同名，则按导入冲突处理，见「测试通用规则」/导入冲突提示）。
       - 9.2 点击新增行 [编辑]，**编辑界面各字段与基准快照 B 一致**（比对口径同第 4 步）。
  10. （可选·环境清理）删除第 9 步导入的 Client，恢复环境。

#### TC-S1 配置管理 + 系统模块

- **优先级**：P1
- **用例目标**：以接口层验证配置读写与系统信息契约——只读项拒绝、上限拒绝、reset 语义、workspaces 去重倒序；依据 `crud-06` 3.1 / 3.2 / 3.3 / 3.4 / 3.5 / 3.6。
- **前置条件**：全新运行目录（`-c {run}`）；已创建 ≥3 条 `job_runs`，覆盖 ≥2 个不同工作区（其中两条 workspace 相同，且该工作区最近使用）；无需界面造数。
- **执行步骤与预期结果**：
  1. `GET /api/system/status` → 预期：恒 200，`{status:"running", uptimeMs, activeRuns}`；`uptimeMs` 为毫秒时间戳字符串，`activeRuns` = 当前 `status IN ('running','terminating')` 的 Run 数（terminating 仍占并发名额，同 `running_count`）。
  2. `GET /api/system/version` → 预期：恒 200，`{version:"0.1.0"}`（`config_version` / `db_version` **不在**本接口，见第 3 步）。
  3. `GET /api/settings` → 预期：200，含顶层 `runDir` 与全部分组（general / client / op / workflow / history / engine / worker / runner / scheduler / log）；`db_path` / `workspace_root` 为**按 runDir 拼接的绝对路径**（下发即绝对路径，不含 `{run}` 占位符）；派生只读项 `worker_pool_size` = `worker_max_concurrency` = `ceil(job_queue_running_max × 1.5)`（默认 15）；`config_version` / `db_version` 只读附加返回；值均为字符串。
     - 3.1 本接口**无错误分支**（恒 200，含配置迁移失败时仍 200 并附加 `migrate_error`）。
  4. `PUT /api/settings` 正常项：`{"log":{"log_level":"debug"}}` → 预期：200 返回更新后全量配置、`log_level=debug`；重读 `{run}/ai-automation.json` 已原子写回（重启后仍为 debug）。
     - 4.1 **只读项拒绝**：`{"general":{"db_path":"..."}}` / `workspace_root` / `config_version` / `db_version` 逐个提交 → 预期：均 **400 `VALIDATION_ERROR`**，message 指明该项只读（**不静默忽略**）。
     - 4.2 **上限拒绝**：`job_queue_waiting_max=1001`（上限 1000）、`workflow_max_nodes=1001`（1000）、`history_max_age_days=181`（硬上限 180）、`job_queue_running_max=11`（上限 10）、`runner_poll_interval_ms=60001`（60000）→ 预期：均 **400 `VALIDATION_ERROR`**；边界值（如 `job_queue_waiting_max=1000`）→ 200。
     - 4.3 `max_loop_multiplier` 例外：`"0"`（不限制）通过且不受上限约束；`"10001"` → 400。
     - 4.4 键/值非法：`{"general":{"no_such_key":"1"}}`、`{"log":{"log_level":"verbose"}}`（枚举外）→ 400 `VALIDATION_ERROR`；`{}`（空对象）→ 200 视为不更新。
  5. `POST /api/settings/reset` → 预期：200 返回全量配置且可配置项回到内置默认（`log_level=info`、`job_queue_waiting_max=20`、`max_loop_multiplier=0` …）；**只读项不参与重置**——`db_path` / `workspace_root` 仍按 runDir 推导、`config_version` / `db_version` / worker 派生项保持原值（不被清空或改写）；无请求体。
  6. `GET /api/workspaces` → 预期：200 `{items:[...]}`；数据源 = `job_runs.workspace` **去重**后按各工作区**最近一次运行时间倒序**（`ORDER BY MAX(created_at_ms) DESC`），不读配置或独立工作区表。
     - 6.1 `limit`：默认 10；`?limit=1` 仅返回最近 1 条；`?limit=abc` → **400 `VALIDATION_ERROR`**（仅参数非法时）。
     - 6.2 `keyword`：`?keyword=ws-00` 仅返回路径含该片段项（LIKE 模糊匹配）。
     - 6.3 一致性：同一工作区多次运行**只出现一次**（去重）；与运行历史筛选下拉的「最近使用」项同源一致。
  7. 落盘核对：`{run}/ai-automation.json` **不含** `db_path` / `workspace_root` / `db_version` / `worker_pool_size` / `worker_max_concurrency`（派生/只读项不落盘；`config_version` 由配置模块维护、存于 JSON）；与 `GET /api/settings` 下发值不矛盾。

### 7. 错误族矩阵（并发 / 循环 / 超时）

> 本组为**错误码与异常状态族**的确定性用例，覆盖现有用例未触及的三类矩阵：并发（`CONCURRENCY_CONFLICT` / `JOB_HAS_ACTIVE_RUNS`）、循环（回跳上限终止）、超时（timeout 状态机与终止语义）。断言口径依据：错误码总表（proposal-02 §10.1）、crud-04 3.4.5/3.4.6/4.5、crud-05 3.5.6/3.5.8/3.5.9、proposal-01 §14/§15。

#### TC-E1a 并发-全局 waiting 触顶 409（queue/parallel 入口）

- **优先级**：P3
- **用例目标**：验证全局 waiting 队列深度上限的统一入口检查——`CONCURRENCY_CONFLICT`（409）在手动运行、单次执行、重跑/重试各入口一致生效；cron 入口不报错（跳过）。
- **前置条件**：临时调低 `settings.job_queue_waiting_max=2`（上限 1000，测试后恢复默认 20）；准备 3 个可 long-run 的 OP（如 sleep 60）；构造 `concurrency=parallel` 的 Job 与 `concurrency=queue` 的 Job 各 1 个；Workflow/OP 均非 needsUpdate。
- **执行步骤与预期结果**：
  1. 先后 [运行] 2 个 long-run 任务（如 Job-A queue、单次执行 OP-B）→ 预期：各返回 `{runId}`，`job_runs` 中 `status='waiting'` 计 2 = waiting_max。
  2. 再手动 [运行] 任意 Job（parallel 或 queue）→ 预期：**409 `CONCURRENCY_CONFLICT`**（message 含全局 waiting 上限），不创建新 Run。
  3. 再单次执行 OP / Workflow / [重跑] / [重试] 任一入口 → 预期：同样 **409 `CONCURRENCY_CONFLICT`**（统一检查，见 crud-04 3.4.6 #3）。
  4. 等待其中一个 waiting 任务被调度转 `running`（waiting 计数降至 1）→ 再运行 → 预期：200（未触顶）。
  5. cron 边界：配置 schedule Job 且当前 waiting 已达上限，等到点 → 预期：**不报错**，本轮跳过（记 error 日志、不创建 Run），不阻塞后续调度。
  6. 恢复 `job_queue_waiting_max=20`。

#### TC-E1b 并发-skip 已有在途实例 409

- **优先级**：P3
- **用例目标**：验证 `concurrency=skip` 的「同 Job 最多 1 个在途实例」判定，**terminating 仍占在途名额**。
- **前置条件**：`concurrency=skip` 的 Job（target=workflow，long-run 节点）；运行历史可用。
- **执行步骤与预期结果**：
  1. [运行] Job → `{runId}`，Run 进入 `waiting` 或 `running`。
  2. 再次 [运行] 同一 Job → 预期：**409 `CONCURRENCY_CONFLICT`**（skip 已有在途）。
  3. 对在途 Run 提交 [终止]（target=workflow）→ Run 进入 `terminating`（等待在跑 OP 收敛）。
  4. **terminating 期间**再次 [运行] 同一 Job → 预期：仍 **409 `CONCURRENCY_CONFLICT`**（terminating 仍占在途名额，见 crud-04 3.4.6 skip 行）。
  5. 等待在跑 OP 收敛、Run 落终态（cancelled）→ 再 [运行] → 预期：200 创建新 Run。

#### TC-E1c 并发-删除 Job 时 JOB_HAS_ACTIVE_RUNS 409

- **优先级**：P3
- **用例目标**：验证「有在途运行时拒绝删除 Job」——`waiting` / `running` / `terminating` 任一存在即 409；仅终态后可删除。
- **前置条件**：Job（target=op，long-run）；先 [运行] 创建在途 Run。
- **执行步骤与预期结果**：
  1. Run 处于 `waiting` → [删除] Job → 预期：**409 `JOB_HAS_ACTIVE_RUNS`**。
  2. 等待 Run 转 `running` → [删除] → 预期：仍 **409 `JOB_HAS_ACTIVE_RUNS`**。
  3. 提交 [终止]（target=op 且已 running → 预期 **409 `RUN_NOT_TERMINABLE`**，OP 运行中不可终止）；改用等待 OP 自然跑完 → Run 落终态。
  4. Run 为终态（success/failed/cancelled/timeout）→ [删除] Job → 预期：200；运行历史中该 Run 保留（名称快照展示，可查看详情、不可跳转 Job 定义）。

#### TC-E1d 并发-边界与恢复

- **优先级**：P3
- **用例目标**：验证并发计数口径的边界值（waiting 触顶边界、恢复后可继续）与 `running_count` 统计（terminating 计入）。
- **前置条件**：同 TC-E1a 环境（waiting_max=2）。
- **执行步骤与预期结果**：
  1. `GET /api/system/status` → 预期：`activeRuns` = `status IN ('running','terminating')` 计数（terminating 计入，同 `running_count`，见 crud-05 4.6）。

  3. 触顶后再 [运行] → 409；待任一 waiting 被调度转 running 后 → 200。
  4. 恢复 `job_queue_waiting_max=20`，再运行 → 预期：200，无残留限制。

#### TC-E2a 循环-on=failure 回跳触顶（retry.max=3）

- **优先级**：P3
- **用例目标**：验证循环回跳上限 `min(max × 3, max_loop_multiplier)`——达到上限时**整个 Run 失败**，且 step_records 执行序列正确。
- **前置条件**：构造 proposal-01 §15.3 拓扑：`Start → A(on=failure 回跳 C → always → A) → End`；A 节点 `retry.max=3`（未配置 backoff 亦可）；A 恒失败；`max_loop_multiplier=0`（默认不限制）。
- **执行步骤与预期结果**：
  1. [运行] Workflow → 预期：Run 最终 `failed`。
  2. 执行次数核对：A 的实际执行次数 = `min(3×3, 0 不限制)` = **9 次**；`step_records` 中 A 共 9 条记录（`(activationSeq, retrySeq)` 序列：activation1 retry1..retry3 → activation2 retry1..retry3 → activation3 retry1..retry3，按 §15.2 每次失败走 C→A 回跳 + activation、retry 重试 + retrySeq）。
  3. 第 9 次执行后不再继续 → 达到上限，整个 Run `failed`；运行历史展示执行次数与失败节点。
  4. `GET /api/runs/{runId}` 详情 → steps 中 A 的记录数与序列与第 2 步一致。

#### TC-E2b 循环-未配置 retry 时 max 取 1

- **优先级**：P3
- **用例目标**：验证「节点未配置 retry 时 `max` 取 1」——执行上限 `1×3=3`。
- **前置条件**：同 TC-E2a 拓扑，但 A 节点**不配置 retry**。
- **执行步骤与预期结果**：
  1. [运行] → 预期：A 实际执行 **3 次**后 Run `failed`（上限 `min(1×3, 不限制)=3`，与 crud-03 4.3.0 ① 口径一致）。
  2. step_records 中 A 共 3 条，retrySeq 均为 1（无重试），activationSeq 1/2/3。

#### TC-E2c 循环-on=success 回跳触顶

- **优先级**：P3
- **用例目标**：验证 `on=success` 循环（A 恒成功 → 回跳）同样受上限约束。
- **前置条件**：构造 §15.4 拓扑：`Start → A(on=success 回跳) → End`；A 恒成功、`retry.max=3`。
- **执行步骤与预期结果**：
  1. [运行] → 预期：A 成功执行 **9 次**（上限 3×3=9）后 Run `failed`（达到上限整个 Run 失败，见 §15.2）。
  2. 与 on=failure 场景对比：循环方向不同、上限计算相同。

#### TC-E2d 循环-max_loop_multiplier 覆盖与 0=不限制

- **优先级**：P3
- **用例目标**：验证 `max_loop_multiplier` 的绝对上限语义与 `0`/未设置 = 不限制。
- **前置条件**：同 TC-E2a 拓扑（A 恒失败、retry.max=3）。
- **执行步骤与预期结果**：
  1. 设 `settings.max_loop_multiplier=2` → [运行] → 预期：A 执行 **2 次**后 Run `failed`（`min(9, 2)=2`）。
  2. 设 `max_loop_multiplier=10001` → 400 `VALIDATION_ERROR`（上限 10000，见 crud-06）。
  3. 设 `max_loop_multiplier=0`（默认）→ [运行] → 预期：不限制（按 `max×3=9` 触顶失败）；若配超时则由超时兜底终止。

#### TC-E3a 超时-单 OP 超时

- **优先级**：P3
- **用例目标**：验证单 OP 执行超时 → Run `timeout`、step `timedOut=true`、按时长终止。
- **前置条件**：OP `timeoutSeconds=1`，content 为 `sleep 5`（bash 类型）或等价长运行；Client 类型匹配。
- **执行步骤与预期结果**：
  1. 单次执行该 OP → 预期：约 1s 后 Run 落 `timeout`（不再等 5s）。
  2. `GET /api/runs/{runId}` → status=`timeout`；step：`timedOut=true`、`timeoutMs=1000`、`durationMs≈1000`。
  3. 运行历史展示超时状态（⏱ 超时）；执行详情展示超时终止语义（§14.3：超时是终止信号，不是失败）。

#### TC-E3b 超时-Workflow 节点超时终止整个 Run

- **优先级**：P3
- **用例目标**：验证 Workflow 中某节点超时 → 整个 Run `timeout` 终止、后续节点不执行。
- **前置条件**：Workflow `Start → A(timeoutSeconds=1, sleep 5) → B → End`（A 超时后 B 不应执行）。
- **执行步骤与预期结果**：
  1. [运行] Workflow → 预期：约 1s 后 Run 落 `timeout`。
  2. 执行详情：A 节点橙框（超时）；B 未执行（⚪）；连线 A→B 不再走。
  3. `GET /api/runs/{runId}` → steps 中 B 无执行记录（或不存在）；`timeoutStepId` 指向 A。

#### TC-E3c 超时-循环场景超时立即终止（不回跳）

- **优先级**：P3
- **用例目标**：验证 §15.7「循环回跳场景下，超时立即终止整个 Run，不再回跳」。
- **前置条件**：on=failure 循环 Workflow（§15.3 拓扑）；A `timeoutSeconds=1`、content 长运行（超时而非失败）。
- **执行步骤与预期结果**：
  1. [运行] → 预期：第一次执行超时后**立即** Run `timeout`，**不再**进入 C→A 回跳。
  2. step_records：A 仅 1 条执行记录（超时），无第 2 次激活；与 TC-E2a 的失败回跳形成对照。
  3. `retry.on=failed` 配置**不**对超时生效（超时 ≠ failed，不自动重试，见 crud-05 3.5.8 / §14.5）。

#### TC-E3d 超时-超时后可手动重试

- **优先级**：P3
- **用例目标**：验证 `timeout` 属可重试的失败 step——`can-retry` 与手动重试闭环。
- **前置条件**：同 TC-E3b 的 Workflow；先超时失败；OP/Workflow 未更新（版本一致、needsUpdate=false）。
- **执行步骤与预期结果**：
  1. `GET /api/runs/{runId}/can-retry` → 预期：`{canRetry:true, reason:null}`（timeout 计入「失败或超时 step」，见 crud-05 3.5.9）。
  2. 运行历史 [重试] 可用 → 确认 → 从失败节点（A）开始重试；若修复 A（缩短执行）→ 最终 `success`。
  3. 对照：`retry.on=failed` 的自动重试对超时**不触发**（E3c 第 3 步），但手动重试**允许**（超时导致 workflow 结束后可手动重试超时 step）。

#### TC-E3e 超时-与 on_failed 自动重试的边界

- **优先级**：P3
- **用例目标**：验证「超时不属于 `on_failed`」——配置 `retry.on=failed` 的节点超时不会自动重试。
- **前置条件**：Workflow 单节点 A（`timeoutSeconds=1`、长运行），节点 `retry={on:failed, max:3}`。
- **执行步骤与预期结果**：
  1. [运行] → 预期：A 执行 1 次超时 → Run `timeout`，**无自动重试**（retrySeq 无递增、A 仅 1 条记录）。
  2. 与失败场景对照：若 A 改为立即失败（exit 1）→ 触发自动重试（retrySeq 1→2→3→4，共 max+1 次尝试后走失败边/终止）。
  3. 结论口径：超时不是 `on_failed` 的触发条件；超时终止的 Workflow 只能手动重试（TC-E3d）。
