ComfyUI、n8n 和 Langflow 是三款设计哲学截然不同的可视化工作流工具。虽然它们都提供图形界面和画布，但核心定位的差异决定了它们在你内网办公场景下的适用性完全不同。

## 相同点

三款工具在形式上有以下共同特征：

- **可视化画布**：都提供基于节点的图形界面，通过拖拽节点和连线来构建工作流
- **节点式架构**：每个节点代表一个独立的功能单元，节点间通过连线传递数据
- **本地可部署**：都支持在本地机器上运行，无需强制依赖云端
- **开源**：核心代码均开源，可自由查看和修改

但这些表面相似之下，内在的定位差异巨大。


## 核心区别

| 维度 | **ComfyUI** | **n8n** | **Langflow** |
| :--- | :--- | :--- | :--- |
| **核心定位** | 扩散模型工作流引擎（图像/视频/3D生成） | 通用工作流自动化 + AI 节点 | LangChain 可视化 IDE |
| **主要开发语言** | Python | TypeScript | Python |
| **AI 能力方向** | **生成式 AI**（图像/视频/音频/3D） | **Agent 编排与自动化**（连接外部系统） | **LLM 链路编排**（RAG、Agent、工具调用） |
| **节点类型** | 模型加载、采样器、ControlNet、图像处理等 | HTTP 请求、数据库、SaaS 集成、Execute Command | LLM、Prompt、Retriever、自定义 Python 组件 |
| **触发方式** | 手动队列、API 调用 | Schedule、Webhook、App 事件、手动 | API、Webhook、Playground |
| **调用本地 CLI 的方式** | 自定义节点（subprocess） | Execute Command 节点（需手动启用） | 自定义 Python 组件（subprocess） |
| **桌面版** | ✅ 有（Windows/macOS） | ❌ 已停止开发 | ✅ 有（Windows/macOS） |
| **适合场景** | AI 绘画/视频生成工作流 | 跨系统自动化、业务集成 | LLM 应用原型、RAG 管道 |

**一句话概括**：ComfyUI 是**生成式 AI 的工作台**，n8n 是**系统自动化的连接器**，Langflow 是**LLM 逻辑的可视化编辑器**。


## 是否适合你的场景

你的核心约束是：**内网办公电脑直接运行，需要调用带数据和权限校验的内部 Agent CLI，且不能因容器或挂载导致权限校验失败。**

### ❌ ComfyUI：不适合

ComfyUI 虽然可以通过自定义节点调用 CLI（社区已有通过 `subprocess` 调用 Codex CLI 的节点示例），也存在 Terminal 节点可以执行 shell 命令，但它的**核心设计目标与你的需求严重错位**：

- ComfyUI 的整个节点体系围绕**扩散模型推理**构建，节点间传递的数据是图像张量、潜空间表示、模型参数等。它**没有为“通用任务编排”设计数据流模型**，用它来编排 CLI 的输入输出会非常别扭。
- 你需要的“DeepSeek 写代码 → Codex 检查 → 不一致则重做”的**条件循环逻辑**，在 ComfyUI 中缺乏原生的流程控制节点，实现成本极高。
- ComfyUI 解决不了你的核心问题——它本身就是一个 Python 应用，在办公电脑上运行确实可以继承你的用户权限，但它的**能力范围完全不匹配**你的任务类型。

**结论：ComfyUI 对你的场景没有实际价值。**

### ⚠️ n8n（npm 裸进程）：有条件可行，但有明显代价

n8n 的 **Execute Command 节点**可以在宿主机上运行 shell 命令，且运行环境就是 n8n 进程所在的主机。如果你通过 `npm install n8n -g` 在办公电脑上裸进程安装 n8n，那么该节点调用的 CLI **会以你的用户身份运行**，理论上可以继承本地权限和环境变量。

但存在两个实质性障碍：

1. **Execute Command 节点被默认禁用**：出于安全原因，n8n 在 2.0 版本中默认禁用了该节点，需要通过修改环境变量 `NODES_EXCLUDE=[]` 手动恢复。这在办公电脑上增加了额外的安全配置负担。
2. **n8n 桌面版已停止开发**：你无法获得一个“开箱即用”的桌面体验，必须自行管理 Node.js 环境和 npm 依赖。

此外，n8n 的核心优势在于**连接大量外部 SaaS 系统**，而你的场景中核心资产是**本地 CLI**。n8n 的 400+ 集成节点在你的内网 CLI 场景中无法发挥作用，你实际上只需要它的 Execute Command 节点和流程控制能力。

**结论：如果你的办公电脑允许安装 Node.js 并接受手动启用安全敏感节点，n8n 可以作为备选。但它并非为“本地 CLI 编排”这一场景优化。**

### ✅ Langflow（桌面版）：最适合

Langflow 提供**原生桌面应用**（Windows/macOS），安装后是一个**本地应用而非容器**。它的**自定义 Python 组件**机制让你可以在组件中使用 `subprocess.run()` 直接调用本地的 Agent CLI。

关键优势在于：**CLI 进程会以你当前登录的桌面用户身份启动**，完全继承你在终端中拥有的所有权限、环境变量（如 `PATH`、内部认证 token）和网络访问能力。如果内部 CLI 的权限校验依赖于“谁在调用”以及“从哪个环境调用”，那么通过 Langflow 桌面版调用的上下文，**与你手动在终端执行是完全一致的**。

Langflow 的官方集成指南中明确展示了通过自定义组件调用 CLI 的模式：一个 Python 类，在方法中使用 `subprocess.run()` 执行 CLI 命令，捕获 `stdout` 并以 `Data` 对象返回。Nylas 的 Langflow 集成就是通过这种方式调用 Nylas CLI 的，认证在 CLI 层面完成，组件本身不处理凭据。

**结论：Langflow 桌面版是三者中唯一真正匹配你场景的工具。** 它的安装最简单，CLI 调用路径与手动在终端执行时的上下文完全一致，能最大程度避免权限校验失败问题。


## 总结

| 工具 | 是否适合你的场景 | 核心理由 |
| :--- | :--- | :--- |
| **ComfyUI** | ❌ 不适合 | 定位为扩散模型生成工作流，不具备通用任务编排能力，与你的 Agent CLI 编排需求完全错位 |
| **n8n** | ⚠️ 有条件可行 | 可通过 npm 裸进程安装并手动启用 Execute Command 节点，但非桌面应用体验，且核心优势无法发挥 |
| **Langflow** | ✅ 最适合 | 提供原生桌面应用，自定义组件直接调用本地 CLI，继承完整用户权限和认证上下文 |

**最终建议**：继续使用 **Langflow 桌面版** 来编排你的内部 Agent CLI 工作流。ComfyUI 和 n8n 在你的场景下都不如 Langflow 合适。
