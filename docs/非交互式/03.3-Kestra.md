# Kestra 与 Langflow 对比及 Kestra 详细介绍

## 一、Kestra 和 Langflow 是同类产品吗？

**不是同类产品。**

Kestra 是**企业级、声明式的工作流编排引擎**，用于可靠地运行数据、AI 和基础设施管道；而 Langflow 是**AI 原生的可视化应用构建器**，专注于拖拽式编排 LLM、RAG 和 Agent 逻辑。


## 二、Kestra 详细介绍

### 核心定位：声明式编排引擎，而非 AI 画布

Kestra 是一个**开源、事件驱动的编排平台**，用 **YAML** 定义工作流，强调“编排即代码”（Orchestration-as-Code）。你声明“要做什么”，Kestra 负责执行、重试、扩缩容和可观测性。它服务于**数据管道、AI 工作流和基础设施自动化**，而非专门用于构建 AI Agent 应用。

### 工作原理

- **一切以 YAML 定义**：每个工作流（Flow）是一个版本可控的文本文件，可纳入 Git 和 CI/CD。
- **语言无关的任务执行**：任务可以用 Shell、Python、Node.js、Go、R 等任意语言编写，在容器或宿主机子进程中运行。
- **丰富的触发方式**：支持 Cron 调度、Webhook、API 调用、事件驱动，以及被其他工作流触发。

### 关键特性

- **多语言支持**：通过容器或 SDK，运行 Python、Node.js、Go、Shell 等脚本。
- **插件生态**：拥有 **1,800+ 插件**，覆盖数据、云服务、AI 工具等。
- **企业级治理**：支持 RBAC、密钥管理、审计日志、命名空间隔离等。
- **实时 UI 与可观测性**：提供 Web 界面查看执行日志、输出、血缘关系。

### 部署与内网支持

- **Windows 裸进程部署**：提供**独立 JAR 包**，无需 Docker，只需 Java JRE 21。可用 `server local` 模式以内嵌 H2 数据库快速启动，适合本地测试。
- **气隙环境支持**：官方明确设计为可在**隔离网络**中运行，Kestra 2.0 的 Worker 不再需要直接连接中央数据库，可部署在分段网络区域。
- **无桌面应用**：Kestra **没有官方桌面应用**，它是一个服务端平台，通过浏览器访问 UI。

### 调用本地 CLI 的能力（关键优势）

Kestra 的 **Process Task Runner** 是一个核心特性，专门用于在**宿主机上以子进程方式执行 Shell 命令或 CLI 工具**，而非在隔离容器中运行。官方 Blueprint 明确说明：“Process task runner executes the command in the same environment as the Kestra worker, so it starts instantly and **inherits the host PATH, binaries, and environment variables**.” 这意味着，如果你的内部 Agent CLI 需要依赖特定的环境变量或系统身份才能通过权限校验，Process Runner 可以让 CLI 在**与手动执行几乎相同的上下文中运行**。


## 三、结合内网办公场景的判断

| 维度 | **Kestra 的情况** | **对你的意义** |
| :--- | :--- | :--- |
| **运行形态** | Windows 独立 JAR，但需运行服务端（含数据库） | 可在办公电脑运行，但**架构较重**，需管理 Java 服务和数据库 |
| **内网/气隙** | ✅ 官方明确支持离线、分段网络 | 适合内网 |
| **权限继承（CLI 调用）** | ✅ Process Runner 在宿主机子进程执行，继承环境变量和 PATH | **与手动执行 CLI 的上下文高度一致** |
| **桌面应用** | ❌ 无 | 通过浏览器访问 UI |
| **AI 能力重心** | 通用编排，AI 作为任务类型之一 | 非 AI 原生，不适合作为 AI Agent 构建工具 |

**结论**：Kestra **技术上完全可以在你的办公电脑上以内网裸进程方式运行**，并且 **Process Runner 调用本地 CLI 的权限继承机制与你的需求高度匹配**。但它是一个**服务端编排平台**，而非轻量的桌面应用，你需要接受运行 Java 服务和数据库的架构复杂度。

如果你的核心目标是**编排内部 Agent CLI 的确定性工作流**（如“DeepSeek 写代码 → Codex 检查 → 重做”），Kestra 是一个**比 n8n 更贴近底层、权限继承更清晰**的可行选择。但如果你追求的是**最轻量、单进程的桌面体验**，Langflow 桌面版仍然是上手门槛最低的方案。


## 四、Kestra 中单个步骤可以是 prompt 还是必须是脚本？

在 Kestra 中，**单个步骤完全可以直接是一个 prompt，而不是必须编写脚本**。Kestra 提供了一系列原生 AI 插件，让你能在 YAML 中直接定义 prompt 并调用 LLM，无需编写任何外部脚本。

### ✍️ Prompt 作为任务属性

Kestra 的 AI 任务（如 `AIAgent`、`ChatCompletion`）将 `prompt` 或 `messages` 作为**核心属性**直接写在 YAML 里。

例如，一个最简单的文本摘要任务，可以直接在 `prompt` 字段中嵌入内容：

```yaml
- id: summarize
  type: io.kestra.plugin.ai.agent.AIAgent
  prompt: "Summarize the following content: {{ inputs.text }}"
```

对于需要更精细控制的场景，可以使用 `ChatCompletion` 任务，通过 `messages` 列表定义 `SYSTEM` 和 `USER` 角色的 prompt。

### 🎯 原生的 AI 任务类型

Kestra 的 AI 插件提供了多种开箱即用的任务，直接接收 prompt 作为输入：

| 任务类型 | 用途 | 关键属性 |
|:---|:---|:---|
| **`AIAgent`** | 运行带工具的 AI Agent，自主决策 | `prompt`、`systemMessage`、`tools` |
| **`ChatCompletion`** | 标准聊天补全，支持多轮对话 | `messages`（含 `SYSTEM`/`USER` 角色） |
| **`Responses`** | 调用 OpenAI Responses API | `input`（可直接是 prompt 字符串） |
| **`JSONStructuredExtraction`** | 从 prompt 中提取结构化 JSON | `prompt` + `jsonSchema` |

这些任务都支持 `{{ }}` 表达式，可以动态引用上游任务的输出作为 prompt 内容。

### 🔗 Prompt 与脚本的协同

虽然 prompt 可以独立成步，但在复杂工作流中，你通常需要将 prompt 与脚本任务结合使用：

- **脚本生成 Prompt**：先用一个 Shell/Python 任务动态生成 prompt 内容（例如从数据库查询、调用内部 API），再将输出传递给 AI 任务。
- **AI 输出驱动脚本**：AI 任务生成文本/JSON 后，下游任务可以用脚本解析结果并执行相应操作（如 `jq` 提取字段、调用 HTTP API）。

### ⚙️ 与你的内部 Agent CLI 场景的衔接

对于你“调用内部 Agent CLI”的需求，Kestra 的 **Process Task Runner** 是关键。它让 Shell 任务在**宿主机上以子进程方式执行**，继承宿主机的 `PATH`、环境变量和系统身份。你可以：

1. **用 AI 任务生成 prompt**（如上文所述，纯 YAML 定义）。
2. **用 Process Runner 的 Shell 任务调用内部 Agent CLI**，将上一步的 prompt 作为参数传入。

这样，prompt 的生成和 CLI 的调用可以在同一个 Kestra 流程中无缝衔接，而 CLI 调用仍然继承你的本地权限上下文。

### 💎 总结

**Kestra 中单个步骤可以是纯 prompt**，通过原生 AI 插件（如 `AIAgent`、`ChatCompletion`）直接在 YAML 中定义即可。它**不强制你编写脚本**，但提供了脚本能力以便在 prompt 前后进行数据准备和结果处理。对于你的内网 Agent CLI 场景，可以将纯 prompt 步骤与 Process Runner 的 Shell 任务组合，实现“prompt 驱动 + 本地 CLI 执行”的完整流程。
