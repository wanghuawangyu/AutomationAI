# Windmill 咨询记录与结论

## 一、Windmill 与 Langflow 是否为同类产品？

**不是同类产品。**

Windmill 是**代码优先的通用工作流编排平台**，而 Langflow 是**专为 AI 工作流设计的可视化构建器**。两者在核心定位、目标用户和能力重心上有本质区别。

### 🎯 Windmill：代码优先的“脚本编排引擎”

Windmill 是一个**开源、可自托管的开发者平台和工作流引擎**，核心定位是**用代码来编排一切**。

- **核心理念**：**Workflow-as-code**。工作流被定义为带有 `@workflow` 和 `@task` 注解的普通 TypeScript 或 Python 脚本，没有 YAML、没有 DSL、没有拖拽。你写的是真正的函数，Windmill 负责处理检查点、并行和容错。
- **主要能力**：将脚本（支持 TypeScript、Python、Go 等）组合成带有分支、循环、审批门和重试的工作流；构建内部工具、数据管道和 API 端点。
- **适用场景**：**内部胶水逻辑、小型自动化、临时任务、一次性脚本、快速 Web 端点**。它擅长将各种脚本和函数“粘合”在一起，但**并非为高并发设计**——每个脚本都会启动一个独立的运行时（256 MB 或更多）。
- **界面**：提供内置的脚本编辑器、流程编辑器和应用构建器，但核心操作是**写代码**，可视化编辑是辅助。

### 🎨 Langflow：AI 原生的“可视化 AI 工作流构建器”

Langflow 是一个**开源的、基于 Python 的 AI 应用程序构建框架**，本质是 **LangChain 的可视化外壳**，专注于**用拖拽的方式编排 AI 能力**。

- **核心理念**：**可视化编排 AI 组件**。在画布上拖拽代表 LLM、提示词、工具、向量数据库、检索器、记忆等 AI 组件的节点，通过连线定义数据流和控制流，无需编写大量代码即可构建 AI 应用。
- **主要能力**：快速构建聊天机器人、文档分析系统、内容生成器和 AI 代理应用；每个工作流都可以一键转换为 REST API 或 MCP 工具，供外部系统调用。
- **适用场景**：**AI 驱动的任务**，尤其是涉及 LLM、RAG 管道和多 Agent 协作的复杂逻辑。它被描述为“AI 大脑”，而非完整的自动化神经系统——如果需要连接 SaaS API、调度任务或处理重试，通常需要将其嵌入到其他平台中使用。
- **界面**：核心就是**可视化编辑器**，通过拖拽和连线完成一切操作。

### 📊 核心差异一览

| 维度 | **Windmill** | **Langflow** |
| :--- | :--- | :--- |
| **核心定位** | 代码优先的通用工作流编排平台 | AI 原生的可视化工作流构建器 |
| **工作方式** | 写 TypeScript/Python 代码，用注解定义流程 | 拖拽 AI 组件节点，连线编排 |
| **主要开发语言** | TypeScript / Python / Go（多语言支持） | Python（基于 LangChain） |
| **AI 能力重心** | 通用脚本编排，AI 作为其中一种能力 | **AI 原生**：LLM、RAG、Agent、工具调用 |
| **目标用户** | 开发者（后端/运维/数据工程师） | AI 工程师、开发者、产品经理 |
| **最佳场景** | 内部工具、数据管道、脚本编排、API 端点 | AI 应用原型、RAG 管道、多 Agent 工作流 |
| **调用本地 CLI** | 通过脚本直接执行 | 通过自定义 Python 组件（`subprocess`） |

### 🔧 Langflow 详解

#### 核心能力

Langflow 的核心是**可视化编排 AI 组件**。它提供预构建的组件库，涵盖 LLM 提供商、向量存储、检索器、工具、记忆、代理等，你可以通过拖拽和连线快速组装出功能性的 AI 工作流。

- **实时测试**：内置 **Playground**，可以在不构建完整应用的情况下测试流，实时查看推理步骤和响应生成。
- **API 与 MCP 服务**：每个流都可以一键转换为 REST API 端点或 MCP 工具，供外部应用集成。
- **自定义组件**：支持编写自定义 Python 组件，突破可视化组件的限制。

#### 调用本地 CLI 的能力

Langflow 通过**自定义 Python 组件**直接调用本地 CLI。核心模式是：编写一个继承自 `Component` 的 Python 类，在方法中使用 `subprocess.run()` 执行 CLI 命令，捕获 `stdout` 并返回为 `Data` 对象。

Nylas 的官方指南展示了这一模式的完整实现：一个组件封装了 Nylas CLI，通过 `subprocess` 调用 `nylas email list --json`，将输出解析为结构化数据供流使用。认证在 CLI 层面完成，组件本身**不处理凭据**。

这意味着：**CLI 进程会以 Langflow 服务运行用户的身份执行**，继承该用户的环境变量、`PATH` 和权限。对于你的内网权限校验场景，这与你手动在终端执行 CLI 的上下文基本一致。

#### 部署方式

Langflow 提供**四种部署方式**，其中**桌面版是上手最简单的方式**——所有依赖已内置，安装后就是一个本地应用，而非容器。

| 部署方式 | 说明 |
| :--- | :--- |
| **Langflow Desktop** | 原生桌面应用（macOS/Windows），所有依赖内置，开箱即用 |
| **pip 安装** | `pip install langflow`，在 Python 虚拟环境中运行 |
| **Docker** | 官方镜像一键启动，适合服务器部署 |
| **源码安装** | 从 GitHub 克隆，适合深度定制 |

#### 主要局限

- **AI 聚焦，非通用自动化**：Langflow 专注于 AI 工作流，如果你需要连接 SaaS API、调度定时任务、处理数据库轮询，需要将其嵌入到其他平台（如 n8n）中。
- **可视化规模化的挑战**：与所有可视化工作流工具一样，节点数量增长后，画布的依赖关系和变量流可能变得难以维护。
- **Python 生态绑定**：核心依赖 Python 和 LangChain，对于非 Python 技术栈的团队可能存在集成摩擦。

### 💎 总结

Windmill 和 Langflow 服务于**完全不同的需求层次**：

- **Windmill** 是**开发者的脚本编排引擎**，强项在于用代码灵活地组合各种任务，适合内部工具、数据管道和通用自动化。它**不专注于 AI**，AI 只是它可以调用的众多能力之一。
- **Langflow** 是**AI 工程师的可视化工作台**，强项在于用拖拽的方式快速构建和调试 AI 工作流，尤其是涉及 LLM、RAG 和多 Agent 协作的场景。它**不是通用自动化平台**，而是 AI 逻辑的专用构建器。

两者可以协同使用：用 **Windmill 或 n8n** 处理通用的系统集成和任务调度，将需要深度 AI 推理的步骤交由 **Langflow** 构建的 AI 工作流来完成。但就“调用带权限校验的内部 Agent CLI”这一核心需求而言，**Langflow 桌面版**通过自定义 Python 组件直接 `subprocess` 调用的方式，仍然是路径最短、权限上下文最一致的方案。

## 二、Windmill 必须自己写脚本吗？Prompt 能作为脚本吗？

**是的，在 Windmill 中，你仍然必须编写脚本。** Prompt 本身**不能**直接作为一个可运行的“脚本”来执行，但它可以作为**生成脚本的输入**，或者作为脚本**内部调用 AI 能力时的一个参数**。

### ✍️ 为什么 Prompt 不能直接作为脚本？

Windmill 的核心设计理念是 **“Workflow-as-code”**（工作流即代码）。它的基本执行单元是 **Script（脚本）**，而脚本的本质是**具有特定入口函数（如 `main`）的真实代码文件**（TypeScript、Python、Go 等）。

平台需要脚本提供明确的**输入参数定义、函数签名和返回值结构**，以便自动生成用户界面、串联工作流步骤，并管理执行状态。一个纯文本的 Prompt 缺乏这些结构化信息，无法被 Windmill 的引擎直接调度和执行。

### 🤖 Prompt 在 Windmill 中的两种实际用法

虽然不能直接当脚本用，但 Prompt 在 Windmill 中有很明确的用武之地：

**1. 作为 AI 生成脚本的输入**
你可以在脚本编辑器或 AI 会话中，用自然语言描述需求，让 Windmill 的 AI 助手**为你生成完整的脚本代码**。例如，你可以输入“写一个调用 OpenAI API 总结文本的 Python 脚本”，AI 会生成包含 `main` 函数、参数定义和 API 调用的可运行脚本。这大幅降低了编码门槛，但最终运行的仍然是 AI 生成的代码，而非 Prompt 本身。

**2. 作为脚本调用 AI API 的参数**
在你的脚本代码内部，你可以将 Prompt 作为**调用外部 AI 服务（如 OpenAI）的参数**。Windmill 支持将 API Key 保存为 **Resource**，然后在脚本中直接引用，向 AI 模型发送 Prompt 并处理返回结果。此时，Prompt 是脚本逻辑的一部分数据，而不是脚本本身。

### 💎 总结

Windmill 的 AI 能力体现在**帮你写脚本**和**在脚本中调用 AI**，而不是**用 Prompt 替代脚本**。它的根基依然是代码。如果你想找的是那种“只写 Prompt 就能跑工作流”的工具，Windmill 不是这个类型；但如果你希望用自然语言加速脚本生成，然后基于生成的代码构建可靠的工作流，Windmill 是合适的选择。

## 三、Prompt 作为脚本参数调用 Agent CLI，是否适合我的场景？

**结论：Windmill 不适合你的场景。** 它能通过脚本调用本地 CLI，但在“办公电脑直接运行”和“内部权限校验”这两个核心约束上存在硬伤。

### ️ Prompt 如何作为参数调用 Agent CLI

Windmill 的设计是 **“脚本包裹一切”**。Prompt 本身不能直接执行，但可以作为**脚本的输入参数**，由脚本来调用 Agent CLI。

你可以创建一个接收 `prompt` 参数的脚本（Python/Bash/TypeScript），在脚本内部通过 `subprocess` 或 shell 命令调用你的内部 Agent CLI：

```python
# Python 脚本示例
def main(prompt: str):
    import subprocess
    result = subprocess.run(
        ["your-internal-agent-cli", "run", "--prompt", prompt],
        capture_output=True, text=True
    )
    return result.stdout
```

Windmill 会自动将这个 `prompt` 参数渲染为 UI 表单或 API 输入，你可以在流程中把上一步的输出动态传给这个参数。

### ❌ 为什么不适合你的场景

虽然技术上能调用 CLI，但 Windmill 在你的两个核心约束上都不成立。

**约束一：办公电脑直接运行（非容器）**

Windmill 确实有**原生 Windows 服务**模式，`windmill-ee.exe` 可以作为服务运行，执行 PowerShell、C# 和 SQL，且**不依赖 Docker**。这看起来符合“办公电脑直接运行”的要求。

但问题在于：**Windmill 的完整运行需要服务端（Server）、Worker 和数据库（PostgreSQL）**。在办公电脑上部署完整 Windmill 实例，意味着你需要在本地运行一个 PostgreSQL 数据库和 Windmill 服务端进程，这对于“只想调用本地 CLI”的场景来说**架构过重**。Agent Worker 模式虽然不需要直接数据库访问，但仍然需要连接到一个远程的 Windmill 服务端。

**约束二：内部 Agent CLI 的数据和权限校验**

这是更根本的问题。Windmill 官方在离线内网环境中存在**已知的依赖拉取问题**。当你运行脚本时，Worker 会**动态从互联网拉取依赖**（如 Deno 的 `mod.ts`），在内网离线环境下会直接失败。官方回复明确指出，解决方式是**使用 Enterprise 版搭建私有注册表，或选择性白名单**——这意味着社区版在内网中的可用性受到严重限制。

即使解决了依赖问题，Windmill 的权限模型是**自身的 RBAC 体系**（基于用户、工作区和路径的权限），而不是继承操作系统用户的身份。脚本以 Windmill 内部定义的“运行身份”（`permissioned_as`）执行，**与你登录办公电脑的操作系统用户是分离的**。如果你的内部 Agent CLI 的权限校验依赖于“当前操作系统用户”或“本地环境变量”，Windmill 的 Worker 进程未必能携带这些上下文。

此外，Windmill 对 AI Agent 执行默认使用 **nsjail 沙箱**，会隔离文件系统和进程。如果你的 CLI 需要访问本地文件或调用其他本地工具，沙箱会进一步增加权限摩擦。

### 📊 与 Langflow 的关键对比

| 维度 | **Windmill** | **Langflow 桌面版** |
| :--- | :--- | :--- |
| **运行形态** | 需要服务端 + Worker + 数据库（即使 Windows 原生模式） | 原生桌面应用，单进程 |
| **内网离线支持** | 社区版存在依赖拉取问题，需 EE 私有注册表 | 桌面版自带依赖，无需联网 |
| **权限继承** | 以 Windmill 内部身份运行，与 OS 用户分离 | **以桌面登录用户身份运行**，与手动执行 CLI 一致 |
| **CLI 调用方式** | 脚本内 `subprocess`，但受沙箱/依赖限制 | 自定义 Python 组件内 `subprocess`，直接继承用户上下文 |
| **架构复杂度** | 高（多组件、数据库、Worker 管理） | 低（单桌面应用） |

### 💎 总结

Windmill 的定位是**“代码优先的脚本编排引擎”**，它的强项是服务端的多语言脚本调度和团队协作，而非在单台办公电脑上轻量地调用本地 CLI。它的**内网离线限制**、**内部权限模型的分离性**以及**多组件架构**，都与你的“办公电脑直接运行 + 内部 CLI 权限校验”需求不匹配。

你之前评估的 **Langflow 桌面版**，通过自定义 Python 组件直接 `subprocess` 调用 CLI，进程以你的桌面用户身份启动，完全继承环境变量和权限上下文，仍然是最匹配你场景的方案。
