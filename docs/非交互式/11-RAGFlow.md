# RAGFlow 与 Langflow 对比及 RAGFlow 详细介绍

## 一、RAGFlow 和 Langflow 是同类产品吗？

**不是同类产品。**

RAGFlow 是**专精于深度文档理解的 RAG 引擎**，核心强项在于将复杂文档转化为高质量的知识库；而 Langflow 是**面向开发者的 LLM 逻辑可视化 IDE**，核心强项在于用拖拽方式精细编排 AI 链路。


## 二、RAGFlow 详细介绍

### 核心定位：企业级深度文档理解 RAG 引擎

RAGFlow 是由 InfiniFlow 开发的开源 RAG 引擎，采用 Apache 2.0 协议，于 2024 年 4 月首次发布。它的核心设计理念是 **“Quality in, quality out”**——通过深度文档理解技术，从复杂格式的非结构化数据中提取高质量知识，为 LLM 提供可靠的上下文层。GitHub Star 数已达 **90.8k**（2026 年 9 月数据）。

### 核心能力：深度文档理解（DeepDoc）

RAGFlow 最突出的能力是其内置的 **DeepDoc** 文档理解模块，能够处理 PDF、Word、Excel、PPT、图片等几乎所有格式，并具备以下关键特性：

| 能力 | 说明 |
|:---|:---|
| **复杂布局识别** | 识别文档的布局、分栏和表格结构，适用于扫描件和格式复杂的文档 |
| **OCR 与表格识别** | 内置 OCR 和表格识别，能准确提取扫描件和复杂表格中的内容 |
| **模板化分块** | 基于文档结构进行智能分块，支持可视化的人工干预和调整 |
| **可溯源引用** | 生成带引用的回答，显著降低幻觉，所有答案可追溯到源文档 |
| **混合检索** | 融合向量搜索（语义相似性）、全文检索（关键词匹配）及知识图谱（实体关系推理），显著提高召回率和精确度 |

### 技术架构与部署

RAGFlow 采用 **Docker 容器化部署**，核心服务包括 RAGFlow Server、MySQL、Elasticsearch、Redis、MinIO 等组件。官方推荐使用 **Docker Compose** 进行编排。

**硬件要求**：CPU ≥ 4 核，内存 ≥ 16 GB，磁盘 ≥ 50 GB。

### 内网/离线支持

RAGFlow **完全支持内网离线部署**。官方和社区均有成熟的离线部署方案：在有网络的机器上拉取所有 Docker 镜像并导出，传输到内网后批量导入即可。配合 **Ollama** 运行本地 LLM（如 DeepSeek），可实现文档、向量、LLM 推理全部本地化，数据不出内网。

### 调用本地 CLI 的能力

RAGFlow 的 **Agent 代码执行组件** 支持多种沙盒提供者，其中 **\`local\` 模式** 明确支持在**当前机器上以本地 Python 或 Node.js 子进程方式运行代码**。官方文档说明：“\`local\`: Runs code as local Python or Node.js subprocesses. Use this only in trusted development environments.”

这意味着：**在受信任的内网办公环境中，你可以配置 RAGFlow 使用 \`local\` 沙盒模式，让代码在宿主机上以当前用户身份执行**。CLI 调用会继承该用户的环境变量、\`PATH\` 和系统权限。**但需要注意**：默认的沙盒提供者是 **Docker 容器**，官方也明确建议 \`local\` 模式**仅在受信任的开发环境中使用**。

此外，RAGFlow 还提供独立的 **\`ragflow-cli\`** 命令行工具（基于 pip 安装），用于后端服务管理和用户生命周期管理，支持列出服务状态、重置密码、控制账户状态等操作。

### 📊 RAGFlow 与 Langflow 核心差异

| 维度 | **RAGFlow** | **Langflow** |
| :--- | :--- | :--- |
| **核心定位** | 深度文档理解 RAG 引擎 | LLM 逻辑可视化编排 IDE |
| **主要开发语言** | Python（后端）+ Go（CLI） | Python |
| **强项** | **文档解析、知识库构建、高精度检索** | **LLM 链路精细编排、自定义 Python 组件** |
| **RAG 能力** | **极强**，DeepDoc + 混合检索 + 重排序 | 节点式手动搭建，需自行配置 |
| **工作流** | 模块化 RAG 流程 + Agent 编排 | 基于 LangChain 的丰富组件库 |
| **调用本地 CLI** | 沙盒 \`local\` 模式支持子进程，默认 Docker 沙盒 | 自定义 Python 组件 \`subprocess\`，直接可用 |
| **部署方式** | Docker Compose（官方唯一推荐） | Docker / pip / **原生桌面应用** |
| **桌面应用** | ❌ 无 | ✅ 有（macOS/Windows） |

### 💎 结合你内网办公场景的判断

| 维度 | **RAGFlow** | **对你的意义** |
| :--- | :--- | :--- |
| **同类产品** | ❌ 与 Langflow 不同类 | RAGFlow 以文档理解与 RAG 为核心，Langflow 以 AI 链路编排为核心 |
| **内网/离线** | ✅ 完全支持，Docker 离线部署方案成熟 | 适合内网 |
| **权限继承（CLI 调用）** | ⚠️ **默认 Docker 沙盒**，需手动切换为 \`local\` 模式 | **默认配置下可能与权限校验不匹配** |
| **桌面应用** | ❌ 无 | 需通过浏览器访问，维护 Docker 服务 |
| **核心价值** | RAG 知识库问答 | 非 CLI 编排工具 |

**结论**：RAGFlow 是**当前开源领域最强大的 RAG 文档理解引擎**。如果你的核心需求是**处理复杂格式的企业文档、构建高精度的知识库问答系统**，RAGFlow 是无可争议的首选。

但就你“**在办公电脑上以裸进程直接调用带权限校验的内部 Agent CLI**”这一核心需求而言，RAGFlow 存在一个**实质性障碍**：它**默认使用 Docker 沙盒执行代码**，CLI 调用继承的是沙盒容器的身份和环境，而非你当前登录的桌面用户。虽然它提供了 \`local\` 模式可以切换到宿主机子进程，但官方明确将该模式标记为**仅限受信任的开发环境**，且需要手动配置，增加了部署的复杂度和不确定性。

如果你能接受在 RAGFlow 中手动配置 \`local\` 沙盒模式，并承担其安全风险，它可以作为调用本地 CLI 的备选方案。但如果你追求**最轻量、单进程、权限上下文天然一致**的桌面体验，**Langflow 桌面版仍然是更匹配你场景的方案**——它的自定义 Python 组件直接使用 \`subprocess\` 调用 CLI，进程以你的桌面用户身份启动，无需任何沙盒配置或安全权衡。
