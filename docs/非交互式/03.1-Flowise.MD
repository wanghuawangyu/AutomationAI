Flowise 和 Langflow 是**同类产品**。它们都是基于 LangChain 的**开源可视化 AI 工作流构建器**，都提供拖拽式画布来编排 LLM 应用、RAG 管道和 AI Agent。两者的核心定位、目标用户和交互方式高度重合，常被作为直接竞品比较。

但它们并非完全相同，关键差异在于技术栈和生态策略。

### 📊 Flowise 与 Langflow 的核心差异

| 维度 | **Flowise** | **Langflow** |
| :--- | :--- | :--- |
| **主要开发语言** | TypeScript / Node.js | Python |
| **底层依赖** | 基于 LangChain（JS 版） | 基于 LangChain（Python 版） |
| **MCP 支持** | ✅ 原生支持 MCP 客户端/服务端节点 | ❌ 不支持 MCP |
| **本地 LLM** | ✅ 支持（Ollama 等） | ⚠️ 部分支持 |
| **自定义逻辑** | 自定义 JavaScript 函数（受限沙箱） | 自定义 Python 代码（更自由） |
| **部署方式** | npm 裸进程安装 / Docker | pip 裸进程 / Docker / **原生桌面应用** |
| **复杂 RAG 性能** | 相对较慢 | 在大型文档 RAG 处理上更快 |
| **画布可维护性** | 节点增多后容易变得混乱 | 相对更清晰，但同样面临规模化挑战 |

两者最显著的技术差异是：**Langflow 不支持 MCP 协议，而 Flowise 原生支持**。如果你未来需要接入标准化协议的工具生态，这是一个关键考量点。


### 🔧 Flowise 详细介绍

#### 核心能力

Flowise 是一个**开源的低代码生成式 AI 开发平台**，用于构建 AI Agent 和 LLM 工作流。它提供三种可视化构建器，复杂度递进：

| 构建器 | 定位 | 适用场景 |
| :--- | :--- | :--- |
| **Assistant** | 最易上手 | 创建能遵循指令、使用工具、从上传文件检索知识（RAG）的聊天助手 |
| **Chatflow** | 单 Agent 系统 | 构建聊天机器人、简单 LLM 流程，支持 Graph RAG、Reranker、Retriever 等高级技术 |
| **Agentflow** | 多 Agent 编排 | Chatflow 和 Assistant 的超集，可创建多 Agent 系统、复杂工作流编排，支持链式、路由、并行、层级、循环等模式 |

#### 关键功能特性

- **编排**：可视化编辑器，支持开源与商业模型、表达式、自定义代码、分支/循环/路由逻辑
- **数据集成**：连接 100+ 数据源、工具、向量数据库和记忆组件
- **部署**：支持自托管和**气隙（air-gapped）部署**，这对内网环境至关重要
- **API/SDK/CLI**：提供 API 访问、JS/Python SDK 和命令行接口
- **安全控制**：RBAC、SSO、加密凭据、密钥管理器、速率限制、受限域名（企业版功能）
- **MCP 集成**：原生支持 MCP 客户端/服务端节点、工具列表、SSE 和认证

#### 部署方式

Flowise 的部署门槛较低，**支持在办公电脑上直接运行**：

**npm 裸进程安装（推荐用于你的场景）**
```bash
npm install -g flowise
npx flowise start
```
启动后访问 `http://localhost:3000` 即可使用。要求 Node.js v18.15.0 或 v20+。

**Docker 部署**
```bash
cd Flowise/docker
cp .env.example .env
docker compose up -d
```

**Flowise 没有官方原生桌面应用**，但 npm 全局安装的方式本质上就是在本地以裸进程运行，进程会以你的当前用户身份执行。

#### 调用本地 CLI 的限制

这是与你的需求最相关的关键点。Flowise 的**自定义工具运行在受限的 JavaScript 沙箱中，不允许使用 `child_process` 模块**，因此**无法直接执行本地 CLI 命令**。

官方推荐的变通方案是：**在本地运行一个轻量 HTTP 包装服务**，由它来执行 CLI 命令，Flowise 的自定义工具通过 HTTP 请求调用这个本地服务。这个包装服务只监听 `127.0.0.1`，约 30 行 Node.js 代码即可实现。

这意味着：Flowise 调用本地 CLI 的路径比你之前评估的 Langflow **多了一层间接性**。Langflow 的自定义 Python 组件可以直接使用 `subprocess.run()` 调用 CLI，而 Flowise 需要额外维护一个本地 HTTP 网关。

#### 主要局限

- **画布规模化困难**：节点超过一定数量后，依赖关系、变量流和权限边界会变得难以维护，适合原型验证但不天然适合长期维护的复杂项目
- **节点生态较窄**：相比 n8n，Flowise 的节点生态更小，社区编写的自定义节点也更少
- **企业功能付费墙**：SSO、工作空间、审计日志等企业级功能位于付费的 Enterprise 版本中
- **复杂 RAG 性能**：在大型文档的 RAG 基准测试中，Flowise 的处理速度慢于 Langflow


### 💎 结合你的内网场景的判断

| 维度 | Flowise 的情况 | 对你的意义 |
| :--- | :--- | :--- |
| **同类产品** | ✅ 与 Langflow 同类 | 可以纳入同一决策篮子 |
| **本地裸进程运行** | ✅ 支持 npm 安装 | 继承当前用户权限 |
| **直接调用 CLI** | ❌ 沙箱禁止 `child_process` | **需要额外维护 HTTP 包装服务** |
| **气隙部署** | ✅ 官方支持 | 适合内网 |
| **桌面应用** | ❌ 没有原生桌面版 | 需要终端启动，但仍是本地进程 |

**结论**：Flowise 和 Langflow 是同类产品，但 Flowise 的**自定义工具沙箱主动阻止了直接调用本地 CLI**，这对于你的“调用内部 Agent CLI”核心需求是一个实质性障碍。Langflow 通过自定义 Python 组件使用 `subprocess` 的方式在这点上更直接。如果你选择 Flowise，需要接受多维护一个本地 HTTP 网关的架构复杂度。
